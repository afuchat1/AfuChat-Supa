Create a dedicated Cloudflare Worker called "afu-cdn" for "cdn.afuchat.com".

The purpose of this Worker is to be the unified CDN/media delivery layer for the entire Afu ecosystem. Keep it completely separate from "afu-api". Do not move API logic into this Worker.

Use a product-first URL structure:

- "cdn.afuchat.com/chat/*" → AfuChat media
- "cdn.afuchat.com/cloud/*" → AfuCloud media
- "cdn.afuchat.com/mail/*" → AfuMail media
- "cdn.afuchat.com/ai/*" → AfuAI media
- Allow additional Afu products to be added later without redesigning the routing architecture.

The CDN Worker should:

- Resolve the product namespace first, then the storage object path.
- Route each product to its correct existing storage/R2 source.
- Preserve existing valid AfuCloud storage and image URLs where applicable; do not migrate or delete existing buckets just to introduce "afu-cdn".
- Support efficient GET and HEAD requests for media delivery.
- Set appropriate long-term caching headers for immutable/static assets.
- Preserve the object's correct "Content-Type" and HTTP metadata.
- Support CORS where appropriate for Afu applications.
- Return clean 404/403 responses for invalid or missing resources.
- Do not treat "/chat/" itself as a storage object key. "chat" is the product namespace, and the path after it is the object key.
- Keep the implementation optimized for high-volume media delivery and avoid routing media through "afu-api".

Security and information disclosure are important:

NEVER expose internal infrastructure details in public responses. Do not expose Worker names, R2 bucket names, bindings, Cloudflare implementation details, internal hostnames, upstream services, stack traces, database information, or internal routing information.

For example, do NOT return responses such as:

{
  "error": "Invalid storage key",
  "worker": "afu-cdn",
  "bucket": "some-internal-bucket"
}

Public errors should remain generic, such as:

{
  "error": "Resource not found"
}

Keep detailed diagnostic information only in internal Worker logs.

The architecture should ultimately be:

"api.afuchat.com" → "afu-api" → API/business logic

"cdn.afuchat.com" → "afu-cdn" → media/object delivery

Do not modify or take ownership of the AfuAuth Worker. Do not change the existing Afu API namespace structure. The goal is to introduce "afu-cdn" as a dedicated, scalable media delivery layer for the Afu ecosystem while preserving existing storage and URLs.

Before making changes, inspect the current "cdn.afuchat.com" routing, existing R2 buckets, object URL conventions, and current AfuCloud storage implementation so the new Worker does not break existing production URLs.
