AfuChat — Diagnose and Fix Production Database Read Layer

Repository: "afuchat1/AfuChat-Supa"

Problem

We are seeing a system-wide data retrieval problem in the AfuChat mobile app.

The application UI looks fine and the newer data actions appear to work. Users can authenticate successfully, and new data actions can appear to create/update data correctly.

However, the app is not reliably fetching the existing data that is already stored in the production database.

This is NOT only a messaging problem.

It affects multiple database-backed areas, including:

- Profiles
- Posts/feed
- Chats/conversations
- Messages
- Followers/following
- Follow counts
- Notifications
- Other existing user-related data

The important observation is:

«The database contains the data, authentication works, and newer data actions work, but the API is not correctly retrieving existing production records.»

The application therefore looks functional on the surface while behaving as though it is connected to an empty or incomplete dataset.

Critical clarification

Authentication is working.

Do not treat login, signup, or the basic authentication flow as the primary problem unless the investigation produces concrete evidence otherwise.

Users can authenticate and obtain a valid session.

The investigation should therefore focus primarily on:

Authenticated request → "afuchat-api" → database query/RPC → production database → returned rows

The main question is:

«Why is "afuchat-api" not correctly retrieving existing production records from the database for an authenticated user?»

2. Verify the database being queried

First prove that "afuchat-api" is querying the same production Supabase database that contains the real AfuChat data.

Inspect the actual Worker configuration and environment variables.

Verify:

- Supabase project URL
- Supabase project reference
- database/API endpoint
- server credentials
- schema configuration
- RPC target
- environment-specific variables
- production vs development configuration
- any legacy Supabase URLs
- any old project references
- any hardcoded database endpoints

Do not assume the configuration is correct simply because requests return HTTP responses.

A Worker can be reachable and authenticated while its database queries are pointed at the wrong project, schema, or data source.

Do not expose secrets in logs or in the final report.

Report only safe identifiers such as project reference where appropriate.

---

3. Verify authenticated identity at the query layer

Authentication itself is working, but we still need to verify that the authenticated identity reaches the database query correctly.

For one real production account, compare:

Mobile Supabase session user.id
        ↓
JWT sub
        ↓
afuchat-api verified user ID
        ↓
database auth.uid()
        ↓
user-owned query/filter

These must refer to the same user.

Do not accept a client-provided user ID as the source of truth for authorization.

The server must derive the authenticated identity from the verified bearer token.

Client IDs may only be used as optional consistency checks.

5. Investigate RPC functions

Audit every RPC used by the affected API routes.

In particular inspect:

get_chat_list
get_or_create_direct_chat

and all other relevant functions used by:

- chats
- messages
- profiles
- follows
- feeds
- notifications
- relationships

For every RPC verify:

1. It exists in the production database.
2. The API calls the correct function.
3. The function is in the correct schema.
4. The function receives the correct parameters.
5. "auth.uid()" resolves to the authenticated production user.
6. The function queries the correct production tables.
7. The function does not accidentally filter out valid records.
8. Security-definer functions have the expected "search_path".
9. Joins do not unintentionally eliminate rows.
10. The returned shape matches what the API expects.

If an RPC returns no rows through the API while the underlying tables contain the records, identify exactly why.

Inspect:

- MMKV cache
- profile cache
- conversation cache
- message cache
- feed cache
- relationship cache
- offline state
- stale state hydration

Determine whether cached data is masking the API/database failure.

The desired behavior is:

Live API/database data
        ↓
update application state
        ↓
optionally update cache

not:

Cache
        ↓
make app look populated
        ↓
silently fail live database request

Cache may be used as a temporary offline fallback, but it must never hide a broken production data path while the user is online.

12. Verify WRITE vs READ divergence

The newer data actions appear to work, so compare their implementation with the broken existing-data reads.

For a representative record:

→ database
→ successful response

READ
→ same database
→ same record

If a write succeeds but a subsequent read cannot retrieve the record, identify exactly where the paths diverge.

Possible causes include:

- different Supabase project
- different schema
- different table
- different API Worker
- different database client
- incorrect query filter
- incorrect user identity
- incorrect RPC
- RLS/auth context
- stale cache

Do not assume that because the write works, the read must be correct.

15. Realtime is not the primary source of historical data

Realtime should not be required to display existing database records.

For example:

- Existing messages must load from the messages API.
- Existing chats must load from the conversations API.
- Existing follows must load from the follow API.
- Existing posts must load from the feed/posts API.

Realtime can update already-loaded state, but it cannot be the mechanism that makes old database records appear.

18. No unnecessary migration

This is primarily a diagnosis and data-access/query problem.

Do not perform database migrations unless you discover a genuine schema mismatch that requires one.

If a migration is technically required:

1. Stop before executing it.
2. Explain exactly why it is required.
3. Identify the affected production resources.
4. Explain the expected impact.
5. Provide a rollback plan.
6. Get approval before executing it.

Existing production data must be preserved.
