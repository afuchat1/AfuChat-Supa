1. CRITICAL API NAMESPACE REQUIREMENT

The AfuChat API namespace is and MUST remain:

/v1/chat/*

DO NOT change it to:

/v1/afuchat/*

There must be NO migration, alias, duplicate route, compatibility route, fallback route, or parallel implementation that introduces "/v1/afuchat/*".

Do not rename existing "/v1/chat/*" endpoints.

Do not create duplicate endpoints under both:

/v1/chat/*
/v1/afuchat/*

That creates unnecessary API conflicts and makes the architecture harder to maintain.

The canonical public contract is:

/v1/chat/*

Examples:

/v1/chat/me
/v1/chat/conversations
/v1/chat/messages
/v1/chat/posts
/v1/chat/feed/for-you
/v1/chat/feed/following
/v1/chat/follows/list
/v1/chat/follows/ids
/v1/chat/follows/summary
/v1/chat/follows/status

All AfuChat functionality exposed through this Worker must remain under "/v1/chat/*".

If existing code or documentation incorrectly refers to "/v1/afuchat/*", correct it to "/v1/chat/*" rather than introducing a second namespace.

Do not create a gateway or routing workaround to support both.

11. Important schema reconciliation

The latest repository shows that the chat system currently contains data across:

afuchat.*

and legacy:

chat.*

The latest implementation recognizes that these datasets cannot simply be treated as identical.

The latest repository audit found:

- shared chat IDs with different membership edges
- legacy-only membership records
- AfuChat-only membership records
- overlapping messages with differing sender IDs
- divergent message-status data
- overlapping posts with differing author IDs
- divergent follow data between current and legacy sources

Therefore:

DO NOT simply switch all queries from "chat.*" to "afuchat.*".

Also:

DO NOT simply switch all queries from "afuchat.*" back to "chat.*".

Do not delete either dataset.

Do not bulk-copy one schema into the other.

Do not assume identical IDs mean identical records.

The latest "get_chat_list" reconciliation must be audited and verified.

20. SECURITY DEFINER EXECUTE GRANTS

There is a separate production security issue.

The production database currently has pre-existing grants where:

- "anon" can execute the six SECURITY DEFINER functions
- "PUBLIC" can execute the direct-chat lookup function

These grants were not introduced by the current migration.

The Worker itself rejects unauthenticated requests.

The repository's intended posture already uses:

REVOKE ALL ON FUNCTION ... FROM PUBLIC;
GRANT EXECUTE ON FUNCTION ... TO authenticated;

Therefore, audit and harden these grants.

Before changing them, identify every legitimate caller.

For each affected function verify:

1. "afuchat-api" caller
2. mobile direct caller
3. frontend caller
4. other backend caller
5. trigger caller
6. scheduled caller
7. service-role caller

Then determine the minimum required execution privileges.

The intended final state should normally be:

PUBLIC          → NO
anon            → NO
authenticated   → YES where legitimately required
service_role    → YES where legitimately required

Do NOT blindly remove "authenticated" or service-role access.

Do NOT assume service-role access is required if the actual API does not use it.

Do NOT change function definitions merely to solve the grant issue.
