Set up and organize the complete API infrastructure for the current AfuChat ecosystem, following the rules below.

If any required infrastructure, configuration, route, binding, database connection, environment variable, secret, documentation, or test is missing, create or configure it immediately, provided that doing so is safe, non-destructive, and consistent with the requirements below. Do not claim that anything was created, configured, deployed, or tested unless it was actually completed and verified.

The immediate development priority is AfuChat, but the API foundation must support all Afu products that currently exist:

- AfuChat
- AfuAuth
- AfuMail
- AfuCloud
- AfuAI
- AfuAds

Do not create APIs or Workers for future products or services that do not currently exist.

1. Required API Workers

The final API Worker names must be:

- "afuchat-api"
- "afuauth-api"
- "afumail-api"
- "afucloud-api"
- "afuai-api"
- "afuads-api"

Use these exact names.

Do not create alternative names such as "afu-api-gateway", "afuchatbackend", "afu-ai-api", or other inconsistent names when the existing service belongs to one of the products above.

If a required Worker is missing, create it immediately after auditing existing infrastructure and confirming that no equivalent implementation already exists. If an equivalent Worker exists under another name, reuse, rename, or restructure it instead of creating a duplicate.

Create or configure any missing required item immediately after the audit, unless doing so would be destructive, require unapproved migration, or conflict with an existing production resource. Document any blocked or deferred item and the reason.

3. Reuse Existing APIs Before Creating Anything

If an existing API already performs the function of one of the required services but has an incorrect name, do not create a duplicate API or Worker.

Instead, rename or reorganize the existing Worker into the correct name.

For example, if an existing Worker is currently called "afu-api-gateway" but its actual responsibility is the AfuChat application API, evaluate it for renaming or restructuring as "afuchat-api".

Likewise, if an existing AfuCloud API has another name, use the existing implementation and reorganize it as "afucloud-api".

Apply the same principle to AfuAuth, AfuMail, AfuAI, and AfuAds.

Rule

Reuse existing implementation → rename or restructure when necessary → preserve existing data → avoid duplication.

Do not create a second Worker simply because the existing Worker has the wrong name.

If renaming is not technically supported without downtime, preserve the existing implementation and configure the required final name through the safest available Cloudflare deployment or routing strategy. Document the exact compatibility and rollback approach.

12. API Gateway and Routing

Do not automatically create a separate gateway Worker.

If "api.afuchat.com" requires a gateway or routing layer because of the current Cloudflare architecture, determine whether "afuchat-api" can appropriately serve that role or whether a separate gateway is genuinely necessary.

Do not create an unnecessary Worker simply to act as a gateway.

The final architecture must clearly document how requests reach each API Worker.

If a routing layer is genuinely required and cannot safely be handled by "afuchat-api", document the reason before creating it, ensure it does not duplicate product functionality, and include it in the final architecture and rollback plan.

"afumail-api" → "afuauth-api"

"afuads-api" → "afuauth-api"

Only create bindings that are actually required.

Do not expose internal services publicly when Worker-to-Worker communication can safely be used.

If a required binding is missing, create and configure it immediately after verifying the target Worker and compatibility. Document every binding and its purpose.

- Migration requirement

18. No Unnecessary Data Migration

Do not migrate data simply because Worker names are changing.

Worker naming and routing should be separated from database ownership wherever possible.

The objective is:

Correct the API architecture without unnecessarily moving the underlying data.

If any proposed change would require data migration, stop before execution unless the migration is technically unavoidable, fully documented, approved, backed up, and reversible.
