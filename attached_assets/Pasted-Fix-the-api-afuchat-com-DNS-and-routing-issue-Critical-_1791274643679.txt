Fix the "api.afuchat.com" DNS and routing issue.

Critical ownership and DNS rule

The domain is managed by both Vercel and Cloudflare, but Vercel owns the wildcard configuration. "api.afuchat.com" has never been linked to a Vercel project and must not resolve through a Vercel wildcard deployment.

"api.afuchat.com" is owned by "afuauth-api".

Do not remove, replace, rename, detach, or otherwise disrupt the "api.afuchat.com" ownership from "afuauth-api".

The existing AfuAuth API must remain fully functional.

The goal is to correct the DNS and Cloudflare routing so that "api.afuchat.com" serves the intended API infrastructure rather than a Vercel wildcard deployment.

Current problem

Requests such as:

https://api.afuchat.com
https://api.afuchat.com/v1/*
https://api.afuchat.com/v1/auth/*
https://api.afuchat.com/v1/chat/*

are currently reaching an incorrect destination and returning a Vercel-style:

Deployment Not Found

"api.afuchat.com" has no Vercel project associated with it. Investigate the actual DNS resolution, Cloudflare proxy configuration, Worker custom-domain configuration, Worker routes, and wildcard interactions to identify why requests are reaching Vercel.

The fix must ensure that "api.afuchat.com" points to the correct Cloudflare/API endpoints and never falls through to a Vercel wildcard deployment.

Required architecture

Keep:

api.afuchat.com → afuauth-api

as the hostname ownership.

The API namespaces should then be routed correctly:

/v1/auth/*   → afuauth-api
/v1/chat/*   → afuchat-api
/v1/mail/*   → afumail-api
/v1/cloud/*  → afucloud-api
/v1/ai/*     → afuai-api
/v1/ads/*    → afuads-api

If Cloudflare requires a hostname-level Worker to receive the request before dispatching individual paths, preserve "afuauth-api" as the owner and use the safest supported Cloudflare routing/service-binding architecture to dispatch the product namespaces.

Do not create a second competing owner for "api.afuchat.com".

Before changing anything

Audit the current configuration first:

- Authoritative DNS records for "api.afuchat.com"
- Whether the record is proxied through Cloudflare
- Nameservers and DNS resolution from multiple public resolvers
- Any CNAME or wildcard record that causes "api.afuchat.com" to resolve toward Vercel
- Vercel wildcard domains and project associations
- Cloudflare Worker custom domains
- Cloudflare Worker routes
- Existing "afuauth-api" configuration
- Existing "afucloud-api" configuration
- Any wildcard routes
- Service bindings
- Current deployment configuration

Identify exactly why "api.afuchat.com" is producing the Vercel-style "Deployment Not Found" response.

Do not make speculative changes.

If the DNS record is missing, incorrectly delegated, pointing to Vercel, or being overridden by a wildcard, correct it so that the hostname reaches the intended Cloudflare/API infrastructure. Do not link the hostname to a Vercel project merely to suppress the error.

Preserve AfuAuth

Do not break any existing AfuAuth functionality.

In particular, preserve:

/v1/auth/*

and all currently implemented AfuAuth authentication flows.

Do not move authentication into another Worker.

Do not create a duplicate authentication service.

Do not replace the existing AfuAuth implementation.

Product Worker isolation

The final architecture must allow independent deployment:

afuauth-api
afuchat-api
afumail-api
afucloud-api
afuai-api
afuads-api

Deploying "afuchat-api" must not redeploy or modify "afuauth-api".

Deploying "afucloud-api" must not redeploy or modify "afuauth-api".

The fact that "api.afuchat.com" is owned by "afuauth-api" must not result in all product APIs being deployed inside the AfuAuth Worker.

Use Cloudflare Service Bindings or the appropriate native Cloudflare routing mechanism where necessary.

Do not break AfuCloud

AfuCloud previously used API infrastructure associated with this hostname.

Before changing any existing routes, identify what AfuCloud currently depends on.

Preserve:

cloud.afuchat.com
img.afuchat.com
cdn.afuchat.com

and existing AfuCloud storage/API functionality.

Do not perform a data migration.

Do not change storage buckets.

Do not change existing object URLs.

Do not remove an old route until the replacement has been verified.

Verification

After fixing the DNS and routing, test the actual hostname and confirm that it no longer resolves to a Vercel wildcard deployment.

At minimum verify:

https://api.afuchat.com
https://api.afuchat.com/v1/auth/...
https://api.afuchat.com/v1/chat/...

and representative routes for:

/v1/mail/*
/v1/cloud/*
/v1/ai/*
/v1/ads/*

Also verify DNS resolution and response headers to confirm that requests are reaching Cloudflare and the intended Afu API infrastructure rather than Vercel.

The root "/" does not necessarily need to be a functional API endpoint. A normal API "404", health response, or documented response is acceptable.

What must not happen is:

Vercel
Deployment Not Found

The response must come from the intended Afu API infrastructure.

Important safety requirement

Do not make destructive or ownership-changing changes to "api.afuchat.com" without first identifying the existing DNS, Cloudflare, Vercel, and Worker configuration and its dependencies.

If the correct Cloudflare architecture requires changing the current hostname routing in a way that could affect "afuauth-api", stop before making that change and report the exact conflict.

The final result must preserve:

api.afuchat.com → afuauth-api ownership

while ensuring that the other "/v1/*" product namespaces function correctly and independently.
