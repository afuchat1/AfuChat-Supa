AfuChat — Migrate and Remove the Legacy "chat" Schema

This is a production consolidation task. Keep "afuchat" as the main and only canonical schema for AfuChat data. Do not create another architecture, schema, or Worker.

1. FINAL ARCHITECTURE

The "afuchat" PostgreSQL schema is the only source of truth for AfuChat data.

- "afuchat.*" = canonical AfuChat database data
- "/v1/chat/*" = canonical AfuChat API namespace
- "afuchat-api" = canonical AfuChat API Worker
- "chat.*" = legacy schema and must be migrated, unused, and removed when safe
- Do not create a new "chat" schema implementation.
- Do not interpret "/v1/chat/*" as PostgreSQL schema "chat".

Final flow:

"Mobile App → https://api.afuchat.com/v1/chat/* → afuchat-api → afuchat.*"

2. RECHECK THE CURRENT PRODUCTION REPOSITORY

Before changing anything:

- Pull the latest "master".
- Inspect recent commits.
- Inspect "afuchat-api".
- Inspect all AfuChat migrations.
- Inspect "afuchat.*" and "chat.*" tables, functions, policies, indexes, triggers, foreign keys, and grants.
- Search the repository for:
  - "chat."
  - "schema=chat"
  - "Accept-Profile: chat"
  - "Content-Profile: chat"
  - ".from("chat"
  - RPCs referencing "chat.*"
  - SQL functions referencing "chat.*"
  - "public.chat_*" where it is a legacy table dependency
  - API configuration selecting the "chat" schema.

Verify the current implementation instead of assuming it is correct.

3. INVENTORY AND MERGE DATA INTO "afuchat"

Inventory every table in "chat" and identify its corresponding "afuchat" table.

Compare:

- row counts
- primary keys
- foreign keys
- overlapping IDs
- timestamps
- ownership and user IDs
- memberships
- messages
- message status
- conversations
- direct chats
- follows
- profiles
- posts
- notifications
- all other AfuChat-owned records.

Determine which records exist only in "chat" and which exist in both.

For overlapping IDs, keep the existing "afuchat" record as canonical. Recover data from "chat" only when an "afuchat" field is demonstrably missing or null and the legacy value is compatible and safe to restore.

Do not blindly overwrite "afuchat" data.

4. PRESERVE DATA AND KEEP ONE COPY

The migration must be non-destructive.

Do not:

- truncate tables
- drop rows before verification
- blindly overwrite "afuchat"
- reset production data
- recreate tables from scratch
- change user IDs
- generate replacement IDs
- delete messages, chats, memberships, follows, profiles, posts, or counters.

Migrate valid records that exist only in "chat" into the matching "afuchat" tables while preserving original IDs and relationships.

When the same data exists in both schemas, keep the canonical "afuchat" record and remove the duplicate legacy copy only after the migration has been verified and rollback/recovery is available.

5. UPDATE FOREIGN KEYS AND FUNCTIONS

After migration:

- "afuchat.*" tables must reference "afuchat.*" tables where applicable.
- No canonical AfuChat table may depend on "chat.*".
- No AfuChat function may query "chat.*".
- No SECURITY DEFINER function used by AfuChat may depend on "chat.*".
- Update all relevant RPCs, including:
  - "get_chat_list"
  - "get_or_create_direct_chat"
  - message-related RPCs
  - membership functions
  - follow-related functions
  - notification-related functions
  - all other AfuChat functions.

Preserve existing behavior and authorization semantics.

6. RLS AND SECURITY

Do not disable RLS.

Audit every affected "afuchat.*" table:

- RLS status
- policies
- authenticated-role access
- "auth.uid()"
- ownership checks
- membership checks
- SECURITY DEFINER functions
- function owners
- "search_path"
- "row_security"
- EXECUTE grants.

Remove obsolete "chat" permissions and dependencies only after confirming they are no longer required.

Do not grant broad "PUBLIC" or "anon" access. Do not place service-role credentials in the mobile app.

7. API MUST USE "afuchat"

Update "afuchat-api" so every AfuChat database operation targets "afuchat".

Keep the existing routes exactly as they are, including:

- "/v1/chat/me"
- "/v1/chat/conversations"
- "/v1/chat/messages"
- "/v1/chat/posts"
- "/v1/chat/follows/list"
- "/v1/chat/follows/ids"
- "/v1/chat/follows/summary"
- "/v1/chat/follows/status"
- "/v1/chat/members"
- all other existing AfuChat functionality under "/v1/chat/*".

Do not create "/v1/afuchat/*", duplicate APIs, aliases, or another gateway Worker.

The API namespace remains "chat"; the database schema is "afuchat".

8. PRESERVE AUTHENTICATION

Preserve the existing identity chain:

"Mobile Supabase session"
→ bearer access token
→ "afuchat-api"
→ "afuauth-api"
→ verified user
→ same authenticated token to Supabase/Postgres
→ "auth.uid()"

Verify that the authenticated UUID is identical at every stage. Do not replace authentication with anonymous access.

9. REMOVE THE LEGACY "chat" SCHEMA

After the data and dependencies are verified:

- remove AfuChat application dependencies on "chat.*"
- remove obsolete "chat" references from production functions
- remove obsolete grants
- remove obsolete routes and configuration
- remove obsolete code paths.

Drop the physical "chat" schema and tables only after confirming:

1. all required data exists in "afuchat";
2. duplicate data has been reconciled;
3. no production function depends on "chat";
4. no Worker depends on it;
5. no mobile client depends on it;
6. no other Afu product depends on it;
7. backups and rollback/recovery are available.

If any dependency or risk remains, do not drop it yet. Make it unused, document it as legacy-only, and keep AfuChat exclusively on "afuchat".

10. VERIFY PRODUCTION FUNCTIONALITY

Verify:

Messages

- authenticated users can retrieve their own messages;
- other users' messages still load;
- "sender_id" is preserved;
- conversations load from "afuchat";
- latest-message data comes from "afuchat".

Chats

- existing conversations load;
- new direct chats can be created;
- memberships are read and written in "afuchat";
- no new chat is created in "chat".

Follows

- follow IDs load;
- follow lists load;
- follow counts load;
- follow and unfollow work;
- all data comes from "afuchat".

Profiles

- "/v1/chat/me" loads the authenticated user's existing profile;
- profile identity matches the authenticated user ID.

Posts and feed

- posts, authors, follows, and feed data load from the canonical "afuchat" source.

11. DO NOT MASK FAILURES

Do not convert database, RLS, schema, or authentication failures into successful empty responses.

Return sanitized errors without exposing:

- Worker names
- internal schema details
- Supabase internals
- SQL errors
- secrets
- stack traces.

12. CREATE A SAFE MIGRATION

Create a production migration that is:

- deterministic
- transaction-safe where possible
- idempotent where possible
- non-destructive
- explicit about conflicts
- safe for existing production IDs.

Use conflict-aware inserts and updates. Do not use a blind "INSERT ... SELECT" that can corrupt existing records.

Before destructive operations, verify backups, recovery, and dependency state.

13. TEST BEFORE DEPLOYMENT

Run all relevant tests, including:

- authentication
- "/v1/chat/me"
- conversations
- messages
- memberships
- direct chat creation
- follows
- posts and feed
- RLS
- SECURITY DEFINER functions
- API error handling
- schema targeting
- absence of "chat.*" production dependencies.

Run a repository-wide search after the changes and confirm that AfuChat runtime code no longer queries the legacy "chat" schema.

14. DEPLOY PRODUCTION

After migration, code, and tests are verified:

1. Apply the production database migration.
2. Verify the production database state.
3. Deploy only "afuchat-api".
4. Do not modify unrelated Workers.
5. Verify "api.afuchat.com".
6. Test authenticated production requests with an authorized test account.
7. Confirm production reads and writes use "afuchat".
8. Confirm no production request touches "chat".

15. SUCCESS CONDITION

The task is complete only when:

Database: "afuchat.*" is the sole AfuChat source of truth.

API: "/v1/chat/*" is the sole AfuChat API namespace.

Worker: "afuchat-api" is the production AfuChat API.

Legacy: "chat.*" is no longer used by AfuChat and is removed when safe.

Application: existing AfuChat users and data continue working without data loss or duplicate records.

Production: authenticated chat, messages, memberships, follows, profiles, and feed data load correctly.

Do not redesign the architecture. Do not create another schema or Worker. Do not migrate AfuChat data into "chat". Keep "afuchat" as the main product schema, migrate any unique legacy data into it, reconcile duplicates by keeping one canonical record, remove the legacy "chat" dependency, verify the result, and deploy "afuchat-api".
