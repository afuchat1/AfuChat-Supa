AFU ECOSYSTEM — MASTER DEVELOPMENT & INFRASTRUCTURE RULES

You are a developer working on ONE product within the Afu ecosystem.

Everyone must focus only on the product they are assigned to. Do not modify, replace, move, or remove anything belonging to another product. If any resource is currently in the wrong place, incorrectly assigned, shared improperly, or otherwise nonconforming, it must be moved or replaced immediately with the correct product-owned resource through a controlled, validated, and reversible migration.

These rules are mandatory. They exist to ensure that independently developed Afu products can share the same ecosystem infrastructure without one product breaking, overwriting, deleting, or changing another product's functionality.

Do not make architectural or infrastructure assumptions. Follow these rules exactly.

---

1. AFU ECOSYSTEM ARCHITECTURE

The Afu ecosystem uses centralized infrastructure with strict product isolation.

All existing infrastructure, configurations, deployments, routes, bindings, schemas, buckets, and integrations must be assessed against the current Afu architecture. Any resource that does not conform to these rules must be migrated to the correct product-owned setup immediately, using a controlled, reversible migration process that preserves existing functionality, data, API compatibility, and security.

No legacy or nonconforming setup may remain in active use once its replacement is ready. Migration must not be delayed merely because the existing setup is convenient, and the current implementation must not be treated as authoritative if it conflicts with this architecture.

However, migration must never be performed blindly. Before changing or replacing any resource, identify its owner, dependencies, consumers, data, routes, bindings, and production impact. Preserve compatibility during the transition, validate the new setup, and remove or decommission the old setup only after successful verification and explicit authorization where required.

Shared public services

api.afuchat.com

Central API domain.

cdn.afuchat.com

Central CDN domain.

Afu Account

Shared ecosystem authentication/identity.

One Database

Shared database with separate schemas.

Product-specific resources

Every product has its own:

- Backend Worker
- Database schema
- R2 storage bucket(s)
- Environment configuration
- Secrets where applicable
- API routes
- Deployment configuration
- Logs and monitoring
- Product-specific code

Any existing resource that combines products, uses an incorrect owner, points to the wrong schema or bucket, or otherwise violates this structure must be migrated to the correct product-specific resource. During migration, maintain service continuity and preserve all required data and contracts.

2. ONE API DOMAIN — NOT ONE SHARED PRODUCT BACKEND

All Afu products use:

https://api.afuchat.com

However, this does NOT mean that all product code must be placed inside one Worker.

The preferred architecture is:

                         api.afuchat.com
                               │
                         API Gateway
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
          ▼                    ▼                    ▼
    AfuChat Worker       AfuCloud Worker       AfuMail Worker
          │                    │                    │
          ▼                    ▼                    ▼
    afuchat schema       afucloud schema       afumail schema

The same pattern applies to AfuAI, Afu Ads, and future Afu products.

A developer must NEVER modify another product's Worker simply because all products use the same API domain.

If an existing implementation places multiple products in one Worker, routes product logic through the wrong Worker, or bypasses product isolation, it must be migrated to the correct independently deployable Workers and gateway routes. The migration must preserve existing endpoints and behavior until all consumers have been moved and verified.

3. PRODUCT OWNERSHIP

Every Afu product owns its own resources.

For example:

AfuChat
├── AfuChat Worker
├── afuchat schema
├── afu-chat-assets bucket
└── AfuChat deployment

AfuCloud
├── AfuCloud Worker
├── afucloud schema
├── afu-cloud-storage bucket
└── AfuCloud deployment

AfuMail
├── AfuMail Worker
├── afumail schema
├── afu-mail-assets bucket
└── AfuMail deployment

The developer must only modify resources belonging to the product they are assigned to.

Any existing resource that is shared incorrectly, ambiguously owned, or assigned to the wrong product must be migrated to the correct owner. Ownership must be documented before migration, and the migration must preserve data, access, routes, secrets, and functionality.

---

4. DATABASE ISOLATION

There is ONE database for the Afu ecosystem.

Each product MUST use its own PostgreSQL/database schema.

Example:

database
│
├── afuchat.*
├── afucloud.*
├── afumail.*
├── afuai.*
├── afuads.*
└── shared.*

Mandatory rules

If you are developing AfuCloud:

You may modify:

afucloud.*

You must NOT modify:

afuchat.*
afumail.*
afuai.*
afuads.*

unless the owner explicitly authorizes a cross-product change.

Never:

- delete another product's tables
- rename another product's tables
- alter another product's columns
- change another product's constraints
- modify another product's migrations
- truncate another product's data
- change another product's schema permissions

If existing product data or tables are located in the wrong schema, use a controlled migration to move them into the correct product schema. Preserve identifiers, relationships, permissions, indexes, constraints, and application compatibility. Do not treat a direct copy, destructive reset, or database-wide migration as acceptable.

---

5. SHARED DATABASE RESOURCES

The "shared" schema is considered critical infrastructure.

It may contain things such as:

- ecosystem identity
- shared accounts
- common configuration
- shared billing infrastructure
- shared permissions
- other explicitly shared resources

Do NOT change shared resources casually.

Before changing anything in "shared", determine:

1. Which products use it.
2. What APIs depend on it.
3. Whether the change is backward-compatible.
4. Whether migration is required.
5. How existing products will be tested.

A product-specific feature belongs in that product's schema, NOT in "shared".

If a product-specific resource currently exists in "shared", it must be migrated into the owning product's schema after all dependencies are identified and compatibility is preserved. Shared resources must not be used as a permanent holding place for convenience.

---

6. ONE CDN DOMAIN — DIFFERENT STORAGE BUCKETS

All Afu products may use:

https://cdn.afuchat.com

However, every product MUST have its own R2 bucket.

Example:

afu-chat-assets
afu-cloud-storage
afu-mail-assets
afu-ai-assets
afu-ads-assets

NEVER use one generic bucket for the entire ecosystem.

Do NOT create a bucket such as:

afu-storage

and put everything into it.

Product ownership must be obvious from the bucket name.

If assets are currently stored in a generic, shared, or incorrectly owned bucket, they must be migrated into the correct product-owned bucket. Preserve object keys, metadata, access behavior, CDN paths, and application references during the migration. Do not delete the source bucket until the migration has been verified and authorized.

---

7. CDN ROUTING

"cdn.afuchat.com" is a shared public CDN domain.

Product-specific paths must identify the owning product.

Example:

cdn.afuchat.com/chat/*
cdn.afuchat.com/cloud/*
cdn.afuchat.com/mail/*
cdn.afuchat.com/ai/*
cdn.afuchat.com/ads/*

Routing should map to the correct product bucket.

Example:

cdn.afuchat.com/chat/*
        ↓
afu-chat-assets

cdn.afuchat.com/cloud/*
        ↓
afu-cloud-storage

cdn.afuchat.com/mail/*
        ↓
afu-mail-assets

A developer must NEVER point another product's CDN path to their own bucket.

A developer must NEVER delete or modify another product's CDN route without explicit authorization.

Any existing CDN route that points to the wrong bucket, uses an ambiguous path, or bypasses product ownership must be migrated to the correct route. Maintain compatibility through redirects or transitional routing where necessary, and verify all affected assets before decommissioning the old route.

---

8. STORAGE SECURITY

R2 buckets must not be treated as interchangeable.

Each Worker should have bindings only to the buckets it needs.

For example:

AfuCloud Worker
        ↓
AFUCLOUD_STORAGE
        ↓
afu-cloud-storage

It should NOT automatically have access to:

afu-chat-assets
afu-mail-assets
afu-ai-assets

unless there is an explicitly approved cross-product requirement.

Least-privilege access is mandatory.

Any existing Worker with excessive, incorrect, or cross-product storage access must be migrated to the correct least-privilege bindings. Remove obsolete access only after confirming that no required functionality depends on it and after the replacement configuration has been tested.

---

9. API ROUTING

API routes must clearly identify the product.

Recommended structure:

api.afuchat.com/afuchat/*
api.afuchat.com/afucloud/*
api.afuchat.com/afumail/*
api.afuchat.com/afuai/*
api.afuchat.com/ads/*

Do not claim or overwrite another product's routes.

Do not silently change another product's API behavior.

Any existing route that does not identify or correctly target its owning product must be migrated to the correct route structure. Preserve existing consumers through versioning, redirects, or compatibility handlers until migration is complete.

---

10. API COMPATIBILITY

Existing API endpoints are contracts.

If another product already depends on an endpoint, do not change its:

- request format
- response format
- authentication behavior
- required parameters
- status codes
- storage paths
- database behavior

without checking its consumers first.

If a breaking change is necessary, use versioning.

Example:

/v1/afucloud/...
/v2/afucloud/...

Do not destroy "/v1" merely because "/v2" exists.

Existing applications must have time to migrate.

When migrating an existing API to the correct Worker, route, or infrastructure, preserve the existing contract during the transition. The migration is not complete until all known consumers have been tested or moved, and the old implementation has been safely decommissioned.

---

11. CLOUDFLARE WORKERS

Each product should have an independently deployable Worker.

Example:

afu-chat-api
afu-cloud-api
afu-mail-api
afu-ai-api
afu-ads-api

Deploying:

afu-chat-api

must NOT replace:

afu-cloud-api
afu-mail-api
afu-ai-api
afu-ads-api

unless an intentional ecosystem-wide deployment is being performed.

If multiple products currently share a Worker or a Worker is incorrectly named or assigned, migrate each product to its correct Worker. Preserve routes, bindings, secrets, scheduled jobs, durable objects, queues, and API behavior during the transition.

---

12. WRANGLER CONFIGURATION

Every Worker must have its own clearly identifiable Cloudflare configuration.

Before deployment verify:

Worker name
Database/schema
R2 bucket bindings
Routes
Environment variables
Secrets
Queues
Durable Objects
Cron jobs
Service bindings
Production configuration

Never copy another product's Wrangler configuration and deploy it without checking every binding.

This is a critical rule.

A copied configuration can accidentally connect one product to another product's database or storage.

Any existing Wrangler configuration that contains incorrect, shared, missing, or ambiguous bindings must be corrected and migrated to the current product-specific configuration. Do not replace configuration without comparing the existing setup, identifying dependencies, and validating the resulting deployment.

---

13. ENVIRONMENT VARIABLES

Environment variables must clearly identify their purpose and product.

Prefer:

AFUCLOUD_API_URL
AFUCLOUD_STORAGE_BUCKET
AFUCLOUD_DATABASE_SCHEMA

rather than vague names where possible.

Never replace an existing ecosystem-wide variable without checking who uses it.

Never commit secrets to GitHub.

Never expose private API keys or service credentials to frontend applications.

Any existing variable that is ambiguous, incorrectly scoped, or points to legacy infrastructure must be migrated to the correct product-specific variable. Maintain temporary compatibility aliases only when necessary, and remove them after all consumers have been migrated and verified.

---

14. AUTHENTICATION

The Afu ecosystem uses a shared account system.

A user should be able to use the same Afu account across products.

For example:

                    Afu Account
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
    AfuChat          AfuCloud          AfuMail
       │                 │                 │
       └──────────── shared identity ──────┘

Authentication is shared infrastructure.

Do not independently redesign authentication inside one product in a way that breaks ecosystem compatibility.

Do not change:

- user ID semantics
- token format
- session behavior
- refresh behavior
- account linking
- authorization claims

without checking all affected products.

If an existing product uses a separate or incompatible authentication setup, migrate it to the shared Afu Account system using a compatibility-preserving transition. Preserve account identity, sessions where possible, authorization behavior, and user access. Do not invalidate or merge accounts without an approved migration plan.

---

15. PRODUCT-SPECIFIC FEATURES

A feature belongs to the product that owns it.

Examples:

Messaging → AfuChat

Storage/projects/domains → AfuCloud

Mailboxes/aliases → AfuMail

AI functionality → AfuAI

Advertising → Afu Ads

Do not put product-specific functionality into another product's Worker just because it is easier.

Any product-specific functionality currently implemented in the wrong Worker, schema, bucket, or service must be migrated to the owning product's infrastructure. Preserve public behavior during the transition and remove the misplaced implementation only after the correct implementation is verified.

---

16. SHARED CODE

Shared code is allowed only when the functionality is genuinely shared.

Examples:

- authentication utilities
- common security utilities
- API validation
- common user identity handling
- shared ecosystem utilities

Shared code must be treated as critical infrastructure because a change can affect multiple products.

Before modifying shared code:

Identify consumers
↓
Check compatibility
↓
Run tests
↓
Deploy carefully
↓
Verify affected products

If existing shared code contains product-specific logic, migrate that logic into the owning product while preserving genuinely shared behavior. Do not duplicate or fork shared infrastructure unnecessarily.

17. DEPLOYMENT INDEPENDENCE

Every product must be independently deployable.

Example:

AfuCloud developer
       ↓
Deploy AfuCloud
       ↓
AfuChat unchanged
AfuMail unchanged
AfuAI unchanged
Afu Ads unchanged

Likewise:

AfuChat developer
       ↓
Deploy AfuChat
       ↓
AfuCloud unchanged

No product deployment should unintentionally rebuild, replace, or delete another product's backend.

Any existing deployment pipeline that can unintentionally affect another product must be corrected immediately. Separate repositories, projects, environments, deployment targets, permissions, and release controls where required.

18. NEVER DELETE UNKNOWN RESOURCES

If you encounter something you do not recognize:

DO NOT delete it.

DO NOT rename it.

DO NOT replace it.

DO NOT assume it is unused.

First determine:

Who owns it?
What uses it?
Which Worker references it?
Which database schema references it?
Which frontend references it?

If ownership cannot be determined, stop and request clarification.

Nonconforming resources must be migrated, not blindly deleted. Decommissioning is permitted only after ownership, dependencies, migration status, backups, rollback procedures, and authorization have been confirmed.

20. BEFORE DATABASE MIGRATIONS

Before running a migration:

Confirm the schema.
Confirm the tables.
Confirm the migration target.
Confirm the environment.
Confirm the affected product.
Confirm backups and rollback procedures.
Confirm all dependent applications.

Never run a migration against the entire database when the change only belongs to one product.

Prefer:

afucloud.some_table

over ambiguous references where appropriate.

When moving data from an incorrect schema to the correct schema, validate row counts, relationships, permissions, indexes, constraints, and application behavior before removing the original data.

---

21. BEFORE STORAGE CHANGES

Before modifying R2:

Confirm bucket name.
Confirm product owner.
Confirm Worker binding.
Confirm CDN route.
Confirm production environment.
Confirm object inventory and migration plan.
Confirm rollback and verification procedures.

Never empty or recreate a bucket as a troubleshooting step without authorization.

Never use another product's bucket as a temporary workaround.

If storage is currently in the wrong bucket, migrate it to the correct bucket while preserving object data, metadata, paths, access controls, and CDN behavior.

22. GIT AND DEPLOYMENT SAFETY

Before pushing changes:

git status

Review exactly what changed.

Do not commit unrelated product changes.

Before deployment, inspect the diff.

Do not overwrite another developer's work.

Do not force-push shared production branches unless explicitly authorized.

Do not remove configuration simply because it is not used by your product.

Infrastructure migrations must be isolated, documented, reviewable, and reversible. Do not combine unrelated cleanup with a migration unless explicitly approved.

---

23. IF YOU DISCOVER A CONFLICT

If your feature requires a resource owned by another product:

STOP.

Do not work around the isolation by modifying that product.

Document:

What you need
Why you need it
Which resource is involved
Which products may be affected
What change is proposed
What migration or compatibility plan is required

Then coordinate with the owner of the affected resource.

If the conflict is caused by an existing nonconforming setup, document the required migration and coordinate with all affected owners before changing shared or cross-product resources.

24. API GATEWAY RULE

The API gateway is the central entry point.

Its responsibility is routing.

It should NOT contain large amounts of product-specific business logic.

Conceptually:

Request
   ↓
api.afuchat.com
   ↓
Identify product
   ↓
Route to correct Worker
   ↓
Product Worker
   ↓
Product schema / product bucket

This keeps the central gateway stable while individual products evolve independently.

Any existing product-specific business logic in the gateway must be migrated into the correct product Worker without changing externally visible behavior during the transition.

---

25. CDN GATEWAY RULE

The CDN follows the same principle.

Request
   ↓
cdn.afuchat.com
   ↓
Identify product path
   ↓
Correct R2 bucket
   ↓
Return asset

The CDN must never become a reason for products to share the same storage bucket.

Any existing CDN configuration that routes assets through the wrong bucket or lacks product identification must be migrated to the correct product path and bucket.

26. OBSERVABILITY AND RESOURCE OWNERSHIP

Every product should be identifiable in:

- Worker logs
- API logs
- CDN requests
- R2 usage
- database queries
- errors
- deployments

Use product identifiers in logs where practical.

Example:

product=afucloud
product=afuchat
product=afumail

This allows the Afu team to determine which product is generating traffic, storage usage, errors, or other resource consumption.

Existing logs, metrics, alerts, and dashboards that do not identify the owning product must be migrated or updated so resource usage and failures can be attributed correctly.

FINAL ARCHITECTURAL PRINCIPLE

The goal is NOT to create completely separate Afu systems.

The goal is to create a single Afu ecosystem with controlled shared infrastructure and independently protected products.

                         AFU ECOSYSTEM
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
   api.afuchat.com      cdn.afuchat.com      Afu Account
          │                   │                   │
     API Gateway          CDN Router        Shared Identity
          │                   │
     ┌────┼────┐        ┌────┼────┐
     ▼    ▼    ▼        ▼    ▼    ▼
   Chat Cloud Mail     Chat Cloud Mail
   Worker Worker Worker Buckets Buckets Buckets
     │    │    │
     ▼    ▼    ▼
   chat cloud mail
   schema schema schema

One Afu ecosystem. One API domain. One CDN domain. One database. One account system.

But every product must remain isolated in its Worker, schema, storage bucket, configuration, routes, and deployment.

All existing and future infrastructure must conform to this architecture. Any setup that does not match must be migrated to the correct product-owned configuration immediately through a controlled, validated, and reversible process.

This isolation is mandatory because a change made by one developer must never unintentionally remove functionality, data, storage, or configuration belonging to another Afu product.
