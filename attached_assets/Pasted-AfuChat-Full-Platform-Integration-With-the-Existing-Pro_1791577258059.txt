AfuChat — Full Platform Integration With the Existing Production Database

Primary Objective

Integrate the entire AfuChat mobile application and its backend with the existing production database schema "afuchat" exactly as it currently exists.

The provided "afuchat" schema is the database contract. The application, API, repositories, services, queries, and data models must adapt to the existing database—not the other way around.

This is an application and API integration task, not a database migration or redesign.

Do not modify the database structure for this task.

1. Strict Database Rules

The existing production database must remain unchanged.

Absolutely do not:

- Create, drop, rename, or alter tables.
- Add, remove, or rename columns.
- Create replacement tables, duplicate tables, or parallel data models in another schema.
- Move or copy records between schemas.
- Run data migrations, backfills, or schema restructuring.
- Create new database functions, RPCs, triggers, indexes, constraints, or policies for this task.
- Change foreign keys, relationships, RLS policies, permissions, or database settings.
- Insert fabricated records, demo data, or seed data to make screens appear populated.

Do not generate or apply database migrations as part of this work. If a feature cannot be integrated without a database modification, document the limitation and request approval separately. Do not make the modification independently.

2. Use the Existing "afuchat" Tables Across the Entire Platform

Inspect the actual production schema and use its existing tables, columns, data types, relationships, and constraints.

This applies to every AfuChat feature, including but not limited to:

- Accounts and profiles: use the existing authentication system and profile relationships.
- Social: posts, follows, follow requests, collections, channels, subscriptions, communities, and related records.
- Messaging: chats, chat members, messages, conversations, participants, media, drafts, folders, labels, preferences, and related records.
- Rewards and economy: gifts, gift transactions, achievements, activity rewards, XP, ACoin transactions, currency settings, and creator earnings.
- Advertising: campaigns, impressions, clicks, and related records.
- Marketplace and commerce: listings, merchants, products, orders, order items, affiliate requests, and freelance services.
- Games: rooms, sessions, scores, and challenges.
- Matching: match profiles, preferences, swipes, matches, messages, gifts, and reports.
- Account and device features: settings, linked accounts, device sessions, login history, blocked users, and other existing records.
- AI and other platform features: existing AfuChat-owned AI, Engagera, email, developer, event, donation, and other feature tables where applicable.

The supplied schema contains relationships to other schemas, including "accounts", "auth", "social", "shop", "rewards", "games", "match", "afuai", and "mail". Inspect and respect these existing relationships. Do not assume that every referenced table belongs to "afuchat", and do not move those tables into it.

For each feature, establish which existing table is authoritative for its records and follow the actual foreign keys and relationships. Do not assume that similarly named tables are interchangeable.

3. Audit the Entire Application Before Changing Code

Perform a feature-by-feature audit of the complete codebase.

For every screen, service, repository, hook, API route, and data-access function:

1. Identify what data the feature needs.
2. Identify the existing production table and columns that hold that data.
3. Verify how related records connect.
4. Identify the current queries, RPCs, schema headers, API endpoints, and fallback behavior.
5. Correct the application code so it reads and writes the existing records through the correct relationships.
6. Remove conflicting application-level assumptions about tables or fields that do not exist in the existing schema.

Do not invent table names, columns, relationships, or new database abstractions and then attempt to make the database support them.

If a required field or feature is not represented in the existing schema, report that gap. Do not create a column or table to fill it.

4. One Source of Truth for Real Platform Data

The existing production database is the source of truth for persisted AfuChat data.

The application must:

- Render real database records returned by the API.
- Use actual database IDs, timestamps, relationships, statuses, and stored values.
- Save user actions to the appropriate existing tables.
- Retrieve persisted changes from the server rather than relying on invented local state.
- Use local caching only for actual server data, with correct synchronization.
- Show genuine empty states when no records exist.
- Report real API or database errors instead of disguising them as empty results.
- Never fabricate profiles, posts, messages, products, campaigns, transaction balances, statistics, notifications, or other records.
- Never silently fall back to a different schema because the correct request failed.

Existing configuration values and genuine UI defaults may be used where appropriate, but they must never be presented as real user or database records.

5. API and Backend Requirements

Keep the existing public API host:

"https://api.afuchat.com"

Preserve established public API routes, including "/v1/chat/*", and other existing routes used by the platform.

Audit the API's schema routing and data-access logic across all features. Remove unintended routing to legacy schemas where it causes AfuChat-owned records to be read from the wrong location.

Do not blindly route every request to "afuchat": authentication, profiles, and related resources may legitimately reference existing tables in other schemas. Follow the actual production schema and relationships while ensuring that AfuChat-owned records use the existing "afuchat" tables.

Preserve authentication, authorization, caller identity, RLS, and existing security controls. Never expose credentials, stack traces, internal Worker names, or private database details in public responses.

6. Protect All Existing Production Data

Do not attempt to fix missing records by merging or copying data from "chat", "social", "public", or other schemas into "afuchat".

If older data is missing from the application, trace the request and determine where the authoritative records already exist. Correct the query, relationship mapping, schema routing, or authorization behavior without modifying database structures or moving records.

If existing tables contain inconsistent or conflicting data, report the exact finding and request direction before taking any data-changing action.

7. Test the Entire Platform

Verify all applicable features against real existing records, using safe test accounts and non-destructive tests.

Check that:

- Existing profiles and account relationships load correctly.
- Existing posts, follows, channels, and subscriptions appear correctly.
- Historical conversations and messages remain accessible.
- Existing rewards, balances, and transaction histories are read accurately.
- Existing marketplace listings, products, and orders load correctly.
- Existing games, matching features, settings, and other supported features retrieve the correct records.
- User actions persist to the intended existing tables.
- Reloading the application preserves actual server state.
- Access controls prevent unauthorized data access.
- Missing records and API failures are handled honestly.
- No new database structures or copied records were introduced.

Test actual API responses and application behavior, not just compilation or successful deployment.

8. Deliverables

Provide a report listing:

1. Each feature audited.
2. The existing tables and relationships used by each feature.
3. Every application/API file changed.
4. Any incorrect schema routing, invalid query, or mismatched data model discovered.
5. Tests performed and their results.
6. Confirmation that no database schema or data was modified.
7. Production deployment status, verified independently from build status.
8. Any unresolved issue requiring approval.

Final Acceptance Criteria

The entire AfuChat platform must use its existing production database structures as provided. The code must adapt to the database, display real existing data, and persist supported actions to the correct existing tables.

No database modifications. No migrations. No copied records. No replacement tables. No invented application data. No unapproved changes.
