COMPLETE AFUCHAT BACKEND MIGRATION

Full Data-Flow Migration — Do Not Redesign the Architecture

You are responsible for completing the AfuChat backend migration correctly and completely.

This is not a request to redesign AfuChat according to your own preferred architecture.

The architecture, ownership boundaries, routing model, shared identity model, storage/CDN model, and product separation have already been defined. Your job is to audit the existing implementation and migrate everything to those boundaries without breaking existing functionality, data, accounts, URLs, or the wider Afu ecosystem.

Repository:

"AfuChat-Supa"

---

1. PRIMARY OBJECTIVE

AfuChat currently has a partially migrated architecture.

Authentication and current-user profile access are now using the centralized AfuAuth/API architecture, but large parts of the application still communicate directly with Supabase.

This must be completed.

The final state must be:

AfuChat Mobile App
        │
        ▼
https://api.afuchat.com/v1/chat/*
        │
        ▼
afuchat-api
        │
        ├── shared Supabase database
        ├── shared AfuAuth identity
        ├── AfuChat product data
        └── AfuChat business logic

AfuAuth remains the centralized identity/authentication authority.

AfuChat remains the owner of AfuChat product functionality and data access.

Do NOT create a second authentication system.

Do NOT create a second user database.

Do NOT create duplicate profiles merely to make the application work.

Do NOT move data into arbitrary new schemas just because they are convenient.

3. SHARED AUTHENTICATION IS NON-NEGOTIABLE

AfuAuth is the centralized identity layer.

There must be one Afu identity.

The same authenticated user must work across:

AfuChat
AfuMail
AfuCloud
AfuAI
AfuAds

The AfuChat app must not create or maintain another independent authentication identity.

For authenticated AfuChat requests:

Authorization: Bearer <AfuAuth/Supabase access token>

The backend must derive the authenticated user from the verified token.

Never trust:

user_id
profile_id
account_id
owner_id

from the client when the value can be derived from the authenticated identity.

The server must establish the authoritative identity.
