---
name: Expo Go QR verification
description: Expo tunnel fallback and bundle checks before sharing a development QR.
---

In this workspace, Expo SDK 58's default tunnel stopped when the Replit-managed Expo CLI session was unavailable. The installed ngrok provider (`expo start --tunnel ngrok`) started successfully without manual Expo authentication and served an Expo Go `exp.direct` URL over HTTP and HTTPS. Expo CLI 58 decides whether to prompt from `process.stdout.isTTY`, so redirecting stdin from `/dev/null` alone may still leave the login/proceed-anonymously menu in Replit workflows. Pipe Expo's combined output through a consumer such as `tee` while leaving `CI` unset; Expo then takes its non-interactive path and proceeds anonymously without disabling Metro reloads. `CI=1` skips the prompt but disables Metro reloads.

Tunnel argument parsing depends on the installed Expo CLI version. If `expo start --tunnel ngrok` reports that the project root ends in `/ngrok`, first compare the resolved Expo/CLI versions with the app manifest and lockfile: a stale SDK 55 install treated `--tunnel` as a boolean, while the app and lockfile targeted SDK 58. Restore dependencies from the pinned lockfile before changing the tunnel command; SDK 58 accepts the ngrok provider form.

Expo Go does not include this app's native WebRTC and Expo AV modules, and Android remote push tokens are unavailable there. The Expo Go workflow sets `EXPO_PUBLIC_IS_EXPO_GO=1` so app guards can skip those optional integrations and active-push-presence requests; keep that override limited to the Expo Go workflow. A development build is required to exercise those native features.

For SDK-managed dependencies, treat `expo install --check` as the compatibility source of truth rather than `pnpm outdated`: npm may have newer patches that the installed Expo SDK does not accept. Use `expo install --fix` to restore the SDK-supported versions, and update unrelated libraries only after compatibility checks.

Do not assume a visible QR is usable: fetch the Android manifest and its actual JavaScript bundle from the QR host, and confirm both return HTTP 200 before sharing the QR. After a major dependency reinstall, clear Metro by default; if preserving a warm cache for faster QR startup, keep it only when both requests succeed.

**Why:** Replit workflows can keep stdout attached to a TTY even when stdin is redirected, which causes Expo CLI to show an unusable account prompt. Setting `CI=1` also skips the prompt but disables Metro reloads, so piping stdout is the better anonymous path. A stale installed CLI can also parse the ngrok provider as a directory argument, even when the lockfile is correct. The phone's generic “Failed to download remote update” message can hide a Metro bundling failure or a tunnel/authentication problem; a QR alone does not prove the bundle is reachable. A verified manifest and bundle can also confirm that a warm cache survived a dependency install. Expo Go can bundle JavaScript successfully while still throwing at runtime if unsupported native modules are evaluated. Newer npm versions can be incompatible with a fixed Expo SDK, so blindly choosing every latest package is not a safe upgrade strategy.

**How to apply:** If the default tunnel requires sign-in and Replit's managed session is unavailable, do not ask for Expo credentials or run manual Expo login. Check that the resolved Expo CLI matches the app SDK and lockfile, restoring with a pinned frozen install if needed. Then use the installed ngrok tunnel provider; keep stdin redirected, pipe combined CLI output so `process.stdout.isTTY` is false, and leave `CI` unset. Request the manifest with Android Expo headers, fetch its `launchAsset.url`, and require HTTP 200 for both before presenting its QR. If either request fails after a dependency reinstall, restart with `--clear`. Keep Expo Go-specific module guards enabled for calls, audio, remote push-token registration, and presence writes.
